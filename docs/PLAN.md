## Порядок реализации

1. **Данные и историческое время.** Сопоставить файлы турбинам, явно настроить
   часовой пояс и смысл десятиминутной метки. Построить почасовые значения
   с количеством исходных измерений. Пропуски целей не заменять нулями.
2. **Погода на момент решения.** Получать конкретный выпуск по координатам.
   Проверять инициализацию и задержку публикации относительно `as_of`.
   Сохранять ответ, URL, параметры и контрольную сумму для воспроизведения.
3. **Базовый прогноз.** Обучить кривую мощности по истории; добавить табличную
   регрессию на CPU. Для совмещения прогноза погоды и телеметрии проверить
   смещение ветра и температуры на обучающем периоде. Сравнить варианты
   на январе 2026, не обучаясь на январских целях. Зафиксировать конфигурацию,
   затем обучить финальную модель на допустимой истории до февраля.
4. **Агент.** Добавить состояние задания, инструменты, проверки, ограниченные
   повторные попытки и анализ результата. При изменении входных данных
   рассчитывать новую версию; одинаковые входы узнавать по контрольным суммам.
   Каждый рассчитанный выпуск турбины сохранять через существующий `ForecastStore`.
5. **API и дашборд.** Реализовать [API](API.md), соединить с фронтом,
   пройти один полный запуск на две турбины и выгрузить CSV.
6. **Воспроизведение февраля.** Последовательно сдвигать момент решения
   на сутки, используя доступные тогда выпуски. Для каждого выпуска сохранять
   собственные 24/48 часов и происхождение данных. Прогнозы за пределами
   февраля помечать отдельно; точный формат сдачи уточнить.
7. **Завершение.** Проверить повторный расчёт, ошибки источника, сохранённый
   погодный кеш, запуск из чистого окружения и документацию.

## Как действует агент

Цель задания: получить прогноз на заданный горизонт для выбранных турбин
при ограничении доступности данных на момент `as_of`.

```text
Проверить запрос и данные
  → найти допустимый погодный выпуск
  → проверить полноту часов и время доступности
  → подготовить признаки
  → выбрать / загрузить подходящую модель
  → получить почасовой прогноз
  → проверить диапазоны, пропуски и резкие изменения
  → сохранить результат, происхождение и пояснение
```

Решения агента зависят от результата инструментов:

- временная ошибка источника → ограниченное повторение запроса;
- выпуск отсутствует → попробовать более ранний допустимый выпуск;
- изменились данные → пересчитать и связать новую версию с предыдущей;
- нет новых данных → вернуть прежний результат с записью в журнале;
- обнаружены некорректные признаки или неподтверждённая доступность погоды
  → завершить задание понятной ошибкой;
- подозрительный, но физически допустимый прогноз → сохранить предупреждение.

Планируется LLM через NVIDIA API для выбора действий среди разрешённых инструментов
и краткого объяснения результата. Числа вычисляет обученная модель, а ограничения
по времени и допустимые действия проверяет сервер. Цикл инструментов ограничен
по числу шагов и времени. Проверяемый режим без ключа использует тот же расчёт
и контроллер с явными правилами; способ управления агентом отображается в результате.
Его наличие и ограничения раскрываются в README.

## Минимальный стек

- Python, FastAPI, Pydantic.
- pandas / numpy для подготовки; scikit-learn для модели.
- HTTP-клиент и файловый кеш исходных погодных ответов.
- DuckDB через существующий `ForecastStore` — история прогнозов, ревизии и факты.
- Долгие задания выполняются в фоне; фронт опрашивает статус и события.
- GPU и Brev — для дополнительных экспериментов при необходимости.

Интеграция с хранилищем: одно задание API на две турбины создаёт две записи
`forecast_runs`; их числовые ID возвращаются как `storage_run_id` в соответствующей
серии. `as_of` передаётся в `issued_at`, время часа — в `ForecastRow.target_ts`.
На границе API принимаем даты с часовым поясом; перед записью приводим их
к UTC и передаём в текущий `TIMESTAMP` без `tzinfo`. Это соглашение внутреннего
хранения не определяет часовой пояс исходного CSV.

Текущий `accuracy_by_lead()` считает ошибки **последнего** прогноза на каждый час.
Для оценки всех повторных выпусков на горизонтах 24/48 часов нужен отдельный
запрос по всем прогнозам с группировкой по выпуску и горизонту.

## Что показать на дашборде

1. Турбины, момент принятия решения и горизонт 24/48 часов.
2. Статус и текущий шаг агента, реальные события и причины повторов.
3. График прогнозной нормализованной мощности отдельно по турбинам.
4. Таблицу времени, мощности, горизонта и использованного погодного выпуска.
5. Предупреждения о данных и источник прогноза погоды.
6. Выгрузку CSV и повторный запуск с проверкой обновления входов.

Подпись мощности: **«Нормализованная мощность, 0–1»**.
До уточнения нормализации и номиналов не подписывать её МВт или МВт·ч.
Фактической мощности февраля в данных нет: график «прогноз против факта»
и метрики февраля до получения контрольных данных недоступны.

## Уточнения, которые нужны от постановщика

- Часовой пояс, начало/конец интервала, время ежедневного выпуска.
- Отдельный результат по турбинам или общий по ВЭС; единицы и нормализация.
- Метрика, веса, шаблон сдачи, обработка последнего 48-часового горизонта.

Эти параметры должны быть явной конфигурацией. Архитектура и интерфейс
могут разрабатываться до получения ответов, итоговую временную разметку
и правила экспорта фиксируем после уточнения.

## Рабочие ориентиры по времени

- Ближайший час: подготовка данных, получение погоды, базовая модель и API.
- Следующий час: автономный цикл и интеграция первого запуска с фронтом.
- Затем: воспроизведение февраля, сравнение моделей, обработка отказов.
- Последний час: сборка, проверка, документация и сдача.

Ориентиры корректируются по фактическим результатам. Каждый час должен
заканчиваться отдельным проверяемым результатом в репозитории.
