# Подключение агента к backend

Дата: 23.09.2026. Публичный формат для фронта — [API.md](../API.md).
Реализация HTTP и очереди: `backend/app/`, точка входа `src/api.py`.

## Разделение работы

| Компонент | Ответственность |
|---|---|
| Backend дашборда | HTTP, валидация, очередь, состояния, события, запись в DuckDB, JSON/CSV, replay |
| Модуль агента | Архивная погода, подготовка, обучение/модель, решения, повторы источника, анализ |
| ForecastStore | Выпуски каждой турбины, точки, факты и ревизии |

Агент вызывается как Python-объект в рабочем потоке одного процесса.
Отдельный HTTP-сервис для него не требуется. Backend вызывает его последовательно.
Внутри `run()` не нужно запускать ещё один HTTP-сервер или повторно записывать
прогнозы через ForecastStore: сохранением владеет backend.

## Фабрика

Переменная окружения:

```dotenv
RENTBOX_AGENT_FACTORY=src.agent:create_agent
```

Имя — согласуемая точка интеграции. На момент написания документа
`src/agent.py` ещё отсутствует; backend не создаёт фиктивную реализацию.

Фабрика без аргументов возвращает объект интерфейса:

```python
from backend.app.integrations.forecasting import AgentContext
from backend.app.schemas.forecast import AgentResult, ForecastRunCreate

class ForecastEngine:
    mode: str  # "policy" или "llm"

    def run(
        self, request: ForecastRunCreate, context: AgentContext
    ) -> AgentResult:
        ...
```

Для явной сборки также доступно `create_app(settings, engine=engine)`.

`mode` — режим при постановке задания. Фактически использованный режим
возвращается в `AgentResult.agent_mode`. При переключении режима по ходу
работы укажите его в `AgentUpdate.agent_mode`.

## Вход

`request`: `as_of`, `horizon_hours`, `turbine_ids`, `refresh_weather`.
Времена уже приведены к UTC. Номера турбин — целые 1/2, без повторов.

`context`:

- `run_id` — строковый ID задания;
- `input_dir` — каталог исходных CSV;
- `source_timezone`, `timestamp_meaning` — подтверждённая интерпретация CSV;
- `turbines` — кортеж конфигураций выбранных турбин с координатами;
- `previous` — предыдущий полный успешный результат для этого же запроса
  и настроек времени либо None;
- `previous_input_sha256` — хеш входов этого результата либо None;
- `emit(update)` — запись фактического события и прогресса;
- `cancelled()` — сигнал остановки сервера.

Часовой пояс CSV не выводится из UTC API. Его и семантику interval_start /
interval_end задают после подтверждения организаторами.

## События

```python
from backend.app.schemas.forecast import AgentUpdate

context.emit(AgentUpdate(
    stage="weather",
    progress=0.2,
    message="Получен допустимый архивный выпуск.",
    tool="weather",
    attempt=1,
    agent_mode="policy",
))
```

Записывайте событие после фактического действия. ID и текущее UTC-время события
добавляет backend. Время журнала — фактическое, `as_of` — историческое.

Этапы: validate, weather, prepare, model, predict, review, save.
Уровни: info, warning, error. Прогресс монотонный; 1 выставляет backend после
успешной транзакции. Финальная проверка и сохранение также добавляют события.
Для внешних запросов нужны явные таймауты и ограниченные повторы.
Проверяйте `cancelled()` между инструментами; `emit()` при остановке
прерывает выполнение. Backend не может принудительно остановить зависший
Python-поток, поэтому таймауты инструментов остаются обязанностью агента.

## Выход AgentResult

| Поле | Требование |
|---|---|
| input_sha256 | 64 строчных hex-символа: хеш полного набора входов и конфигурации |
| agent_mode | Фактически использованный llm или policy |
| model_name, model_version | Название и воспроизводимая версия модели |
| training_data_available_until | Последняя доступная обучающая цель; не позже as_of |
| series | Ровно по одному объекту на запрошенную турбину |
| analysis | summary и список warnings |

Серия: `turbine_id`, `points`, `weather`.
Числовые `storage_run_id` добавляет backend после записи.

Каждая точка: `valid_time`, `lead_hour`, `predicted_power`.
Ровно 24/48 точек, по возрастанию lead_hour от 1.
`valid_time = as_of + lead_hour часов`; мощность конечная и в диапазоне 0–1.

`weather`: provider, model, initialization_time, available_at,
availability_basis, retrieved_at, sha256. Все даты с зоной.
Backend проверяет:

```text
initialization_time <= available_at <= as_of
available_at <= retrieved_at
training_data_available_until <= as_of
```

retrieved_at может быть сегодняшней датой при скачивании исторического архива.
Значение available_at требует реального обоснования в availability_basis.

## Хеш входов и повторные расчёты

В input_sha256 включить каноническое представление:

- SHA-256 исходных измерений и погодных ответов;
- версии модели, признаков и обработки;
- параметры запроса, настройки времени и доступности;
- все остальные входы, меняющие числовой результат.

Не включать текущий run_id и время повторного скачивания неизменённого архива.
SHA погодного ответа остаётся отдельным полем weather.sha256.

Агент может сравнить проверенные входы с данными предыдущего результата и
переиспользовать расчёт. Backend сравнивает хеш с сохранённым хешем предыдущего
запуска: при совпадении сохраняет ссылку reused_run_id без дублирования точек.
Возвращаемые числа и происхождение должны совпасть с прежними; расхождение
при одинаковом хеше считается DATA_QUALITY_ERROR.

При новых входах backend создаёт новую ревизию и оставляет прежнюю.
В контексте передаются предыдущие метаданные, точки и previous_input_sha256;
внутренний input_sha256 не включён в публичный ответ для фронта.

## Ошибки

Ожидаемые ошибки инструментов:

```python
from backend.app.core.errors import AppError

raise AppError(
    503, "WEATHER_UNAVAILABLE",
    "Не найден доступный погодный выпуск для выбранного момента.",
    retryable=True,
)
```

Из фонового задания ошибка попадёт в status=failed и поле error.
Текст AppError показывается пользователю: не включать ключи и служебные ответы.
Неожиданные исключения пишутся в серверный журнал; клиент получает MODEL_ERROR.
Некорректный результат — DATA_QUALITY_ERROR.

## Хранение

Backend создаёт запись на каждую турбину через `record_run`, затем
`record_forecast`. `as_of` становится `issued_at`; UTC-время сохраняется
без tzinfo в соответствии с текущей схемой ForecastStore.

Все записи обеих турбин и завершение API-задания входят в одну транзакцию.
Дополнительные таблицы api_runs/api_replays хранят состояния, запросы,
метаданные погоды, ссылки ревизий и ответы. Сам файл DuckDB не коммитится.

При перезапуске незавершённые задания переходят в JOB_INTERRUPTED.
История готовых запусков и прогнозов сохраняется. Отдельный worker-процесс
и одновременная запись из CLI в ту же БД в этой версии не поддерживаются.
