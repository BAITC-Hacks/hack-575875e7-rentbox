# DuckDB — контекст для следующих задач

Документация изучена 23.09.2026 по [официальному указателю](https://duckdb.org/docs/current/). На момент чтения `current` относится к ветке 1.5, страница Python API указывает 1.5.5. Версию зависимости фиксировать при подключении.

## Решение пользователя

DuckDB используется вместе с FastAPI. Предыдущее общее указание «без БД» уточнено
выбором DuckDB. После изучения документации пользователь поручил реализовать
backend по контракту команды. Установлена и закреплена версия 1.5.5.

## Изученные разделы

| Раздел | Что учитывать |
|---|---|
| [Python API](https://duckdb.org/docs/current/clients/python/overview) | Явные соединения, SQL и Relation API, чтение файлов, преобразование результатов и экспорт. Relation вычисляется при запросе результата. |
| [Python DB API](https://duckdb.org/docs/current/clients/python/dbapi) | `connect()`, память или файл, `read_only`, `execute`, получение результатов, закрытие ресурсов. Параметры запроса передавать отдельно от SQL через плейсхолдеры. |
| [CSV](https://duckdb.org/docs/current/data/csv/overview) | Прямое чтение и загрузка в таблицу, автоматическое определение формата и явное задание колонок/типов. Для повторяемого импорта закреплять формат после изучения реальных файлов. |
| [Parquet](https://duckdb.org/docs/current/data/parquet/overview) | Прямые SQL-запросы к одному или нескольким файлам, фильтрация и выбор колонок при чтении, запись результатов. |
| [Конкурентный доступ](https://duckdb.org/docs/current/connect/concurrency) | Для обычного встроенного режима: чтение/запись одним процессом; несколько процессов могут открывать файл только для чтения при отсутствии писателя. Потоки внутри одного процесса поддерживаются с учётом конфликтов записи. |
| [Потоки Python](https://duckdb.org/docs/current/guides/python/multiple_threads) | Пример использует локальный для потока handle через `.cursor()`. DB API отдельно описывает сериализацию запросов на общем соединении; не предполагать параллельность из-за наличия нескольких handles. |
| [Типы времени](https://duckdb.org/docs/current/sql/data_types/timestamp) | Различать `TIMESTAMP` и `TIMESTAMPTZ`; явно определить часовой пояс входных измерений и прогнозов. |
| [Настройки](https://duckdb.org/docs/current/configuration/overview) | `threads`, `memory_limit`, `temp_directory`; значения подбирать по данным и ресурсам Mac. |

В текущей документации также описан Quack для удалённого доступа из нескольких процессов; это отдельная архитектура. Его использование в проекте не согласовано. Источник — раздел конкурентного доступа.

## Выводы для будущей реализации

Это инженерные рекомендации по контексту проекта, а не уже реализованные возможности:

- Время жизни соединений согласовать с `lifespan` FastAPI; освобождать ресурсы при завершении.
- Выполнение блокирующих SQL-запросов учитывать при выборе синхронных/асинхронных обработчиков.
- Число процессов Uvicorn выбирать после определения режима чтения и записи. Несколько воркеров не должны независимо открывать один файл для записи в обычном встроенном режиме.
- Для дашборда вычислять нужные фильтры и агрегаты в SQL, ограничивать объём ответа API.
- Для кейса ВЭС различать время измерения, время публикации погодного прогноза, момент принятия решения и целевой час. Соединение рядов не должно добавлять данные из будущего.
- Для первой реализации выбран файл `data/forecasts.duckdb`; в Docker — отдельный том.

## Статус каркаса

Backend использует `src/storage.py` через `ForecastStore`, без ORM и миграционного
фреймворка. Таблицы коллеги не изменены; `api_runs` и `api_replays` дополняют их
состояниями заданий, событиями и происхождением результатов. Доступ сериализован
в одном процессе, запись обеих турбин и завершение задания транзакционны.
Подробности: [agent-integration.md](agent-integration.md), [backend](../../backend/README.md).
OpenAPI экспортирован, Ruff выполнен. Тесты, Docker-сборка и полный сценарий
с реальным агентом пока не проверены.
