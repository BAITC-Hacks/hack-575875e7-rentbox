## Общая схема

```
Соревновательная часть 23.09, 13:00–18:00 (п. 5.3.1, 3.5)
        │  итоговая версия = содержимое репо на 18:00 (п. 5.4.13)
        ▼
Первичная проверка: соответствие условиям, комплектность, работоспособность (п. 5.6.1)
        │  не запускается по README → НЕ допущены, пояснения не принимаются (п. 5.4.16, 5.6.5)
        │  требует личный аккаунт участника → нарушение п. 5.6.6
        ▼
Техническая оценка по критериям ТЗ Задачи + вспомогательные AI-судьи (п. 5.5.1, 5.6.2, 4.2–4.4)
        │  результаты разных задач приводятся к единой шкале / нормализуются (п. 5.5.4)
        │  порядок и число финалистов определяет Организатор (п. 5.6.7)
        ▼
Финалисты → Demo Day 29.09: 100 баллов (п. 5.7.2), итог — коллективное решение Жюри (п. 5.7.3)
        │  10 Задач, единый зачёт, 10 призовых мест, без квот (п. 5.8.1)
        ▼
Победители → награждение 01.10 на AI & Digital Bridge
```

Принципы (п. 5.5):

- Критерии оценки конкретной Задачи определяются **её техническим заданием** (п. 5.5.1–5.5.2).
- Применяются **только** условия и критерии, опубликованные для Задачи **до начала соревновательной части** (п. 5.5.3).
- Критерии и правила начисления баллов **могут различаться** между задачами; для общего рейтинга результаты приводятся к единой шкале, нормализуются или ранжируются в порядке, установленном Организатором (п. 5.5.4).
- ТЗ и критерии могут писать постановщики задач, партнёры или технические эксперты; Организатор только публикует утверждённую версию и не обязан её дополнять (п. 5.5.5).
- После старта ретроспективно менять обязательные требования, критерии техоценки и порядок отбора нельзя (п. 6.4).

### 1.1 Запускаемость — условие допуска, не баллы (п. 5.4.16, 5.6.5)

> «Если итоговую версию Проекта не удаётся запустить по инструкциям, размещённым в Репозитории, Команда не допускается к дальнейшему отбору. Дополнительные пояснения и исправления не принимаются.»

Это самое жёсткое место новой редакции: раньше эксперты могли запросить пояснения по окружению — **теперь не могут**. Один неработающий шаг в README = вылет.

**Что делать:**

- Запуск **одной командой** из чистого клона: `docker compose up --build` или `make run` / `./run.sh`. Docker — самый надёжный способ гарантировать чистое окружение.
- Зафиксированные версии зависимостей (`requirements.txt` с версиями, lock-файлы).
- **Обязательная репетиция:** `git clone` в пустую папку → пройти README буквально, командой за командой → всё работает. Скрипт `scripts/check-clean-env.sh` делает ровно это.
- Демо-данные — **в репозитории** (или скрипт генерации), чтобы сценарий проверялся без внешних доступов.
- Никаких «сначала установите X вручную» без указания точной команды.

### 1.2 Проверяемость без личных аккаунтов (п. 5.6.6) — новое требование

> «Команда обязана обеспечить возможность проверки ключевой функциональности Проекта без необходимости использования личных аккаунтов участников, персональных подписок или закрытых учетных записей. В случае использования внешних сервисов, API или иных инструментов команда обязана предоставить необходимые демонстрационные доступы, тестовые учетные записи либо иные способы проверки работы решения.»

Прямо бьёт по схеме «положим ключ в `.env`, пусть жюри подставит свой».

**Что делать:**

- Если решение ходит во внешний LLM/API (NVIDIA API, OpenAI и т. п.) — предусмотреть **один из**:
  - демонстрационный ключ/тестовую учётку, приложенную к проекту в порядке, разрешённом сервисом;
  - **fallback-режим без внешнего ключа**: детерминированная локальная логика или заранее записанные ответы, чётко помеченные как демо-режим, при этом основная функциональность под Задачу должна оставаться настоящей;
  - локальную модель/алгоритм, работающий на CPU без ключей.
- В README — явный раздел: «Как проверить без своих ключей» с точными шагами.
- В `.env.example` — комментарий, что происходит, если переменная не задана.
- Ошибка при отсутствующем ключе должна быть понятной («не задан NVIDIA_API_KEY, см. README §8»), а не traceback.

> «README-файл должен позволять техническим экспертам понять принцип работы решения и самостоятельно выполнить его развертывание» (п. 5.4.15).

Дополнительно к обязательному минимуму держим в README то, что требуют другие пункты Положения:

- **Внешние материалы** — раскрытие сторонних библиотек, моделей, датасетов, шаблонов с источниками и лицензиями (п. 5.4.4, 5.4.4.1, гарантии п. 6.1.7).
- **Заранее подготовленные компоненты** — что из заготовок использовано и почему это не основная функциональность (п. 5.4.4.2).
- **AI-инструменты** — чем пользовались (Codex и прочее, п. 5.4.12).
- **Вклад участников** — эксперты и жюри проверяют фактический вклад каждого (п. 5.4.7, 4.6).
- **Ограничения и что не реализовано** — честно; если что-то замокано, сказать прямо.

Баллов за README в Положении больше не назначено, но его отсутствие или неполнота = нельзя развернуть = п. 5.4.16.

### 1.4 Репозиторий и история разработки (п. 5.4.8–5.4.11)

- Основная разработка — **только в репозитории платформы**, он же единственный основной рабочий репозиторий, с подтверждаемой историей (п. 5.4.9, 5.4.11). Сторонние закрытые репозитории — основание для дисквалификации (п. 5.9.2).
- **Каждый отчётный час — подтверждённый промежуточный результат** (п. 5.4.8). Засчитываются: изменения в коде/репозитории, разработанный функционал, прототип, дизайн, схема архитектуры, настроенная модель, проведённое тестирование, подготовленные данные. Отсутствие → дисквалификация (п. 5.9.2).
- Организатор проверяет историю разработки, метаданные файлов, работоспособность и **фактический вклад каждого участника** (п. 5.4.7). История коммитов должна показывать эволюцию, а не один коммит «final».
- Итоговая версия — содержимое на **18:00**, независимо от момента блокировки интерфейса платформы (п. 5.4.13). Изменения после не учитываются нигде, включая Demo Day (п. 5.4.14).

### 1.5 Что можно и нельзя приносить с собой (п. 5.4.4.2, 5.4.5)

Новая редакция явно разрешает заготовки — этого в прошлой не было:

> «Командам разрешается использовать заранее подготовленные технические компоненты, инструменты разработки, собственные библиотеки, шаблоны и инфраструктурные решения, если они не являются готовым продуктом или основной частью решения… Основная функциональность Проекта, соответствующая Задаче Хакатона, должна быть разработана в рамках Соревновательной части.»

- Шаблоны из `templates/`, скрипты, Docker-обвязка, клиенты API — **можно**, с раскрытием в README.
- Готовый продукт, который до 13:00 уже умел то, что заявлено как результат хакатона, — **нельзя** (п. 5.4.5).
- Open-source — можно при соблюдении лицензий и раскрытии; нарушение — это использование чужого решения без раскрытия источника или выдача его за своё (п. 5.4.4.1).

### 1.6 Надёжность

Отдельного критерия «надёжность» в Положении больше нет, но первичная проверка включает работоспособность (п. 5.6.1), а неработающий сценарий — это провал по п. 5.4.16. Минимум:

- Валидация входов (пустые поля, неверные типы, отсутствующие файлы, некорректные диапазоны) → понятная ошибка, а не traceback.
- `try/except` на внешних вызовах (API, файлы, БД) с осмысленными сообщениями.
- Нет секретов в коде и в репозитории; нет `eval` на пользовательском вводе.
- Smoke-тест одной командой — показывает, что основной сценарий не падает.

## Этап 2. Demo Day (29.09) — 100 баллов (п. 5.7.2)

Оценивается **та же итоговая версия** (п. 5.4.14) — новых фич показывать нельзя. Жюри может просить показать отдельные функции, проверять работоспособность и уточнять вклад каждого участника (п. 4.6).

**Важно про подсчёт (п. 5.7.3):** предварительные баллы членов жюри — инструмент для обсуждения. Итоговое распределение мест определяется **коллективным решением Жюри**, которое имеет приоритет над арифметическим рейтингом. Среднего арифметического и формального tie-break, как в прошлой редакции, больше нет. Право на место возникает только после утверждения итогового протокола (п. 5.7.4).

Сам перечень критериев «носит ориентирующий характер» — жюри вправе само определять значимость характеристик проекта (п. 5.7.2).

### 2.1 Ценность решения — 25 (самый весомый)

> «Насколько проект решает реальную и понятную проблему. Насколько значимую пользу решение дает целевой аудитории и насколько эта польза очевидна из презентации и демонстрации.»

- Начинать питч с **проблемы и цифр** (для энергетики: потери, простои, штрафы, ₸/кВт·ч, МВт, часы).
- Явно назвать целевого пользователя (диспетчер, энергосбыт, потребитель, регулятор) и что он получает.

### 2.2 Результат и качество решения — 20

> «Насколько представленный продукт или прототип действительно позволяет реализовать заявленный сценарий. Оценивается целостность решения и качество пользовательского результата, без повторной технической проверки кода.»

- Живое демо сквозного сценария на реалистичных данных. Иметь запасную видеозапись демо на случай сбоя.

### 2.3 Инновационность — 15

> «Насколько решение предлагает новый или нестандартный подход к задаче, отличается от очевидных альтернатив и имеет собственное преимущество.»

- Один слайд «чем отличаемся от очевидного решения и существующих аналогов».

### 2.4 Потенциал развития и масштабирования — 20

> «Насколько проект может получить дальнейшее применение после хакатона, расширяться на новых пользователей, организации, отрасли или сценарии использования.»

- Roadmap: что дальше, на какие объекты/регионы/отрасли масштабируется, что нужно для пилота.

### 2.5 Презентация, демо и ответы на вопросы — 20

> «Насколько понятно команда раскрыла проблему, решение и его преимущества; насколько убедительно продемонстрировала результат и смогла ответить на вопросы жюри.»

- Структура: проблема → решение → демо → отличия → потенциал → команда. Репетиция с таймером.
- Заранее подготовить ответы: «что сделано за 5 часов, а что было до» (п. 5.4.4.2), «какие данные и под какой лицензией», «вклад каждого», «как масштабировать», «что если данных нет».
