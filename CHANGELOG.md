# ChangeLog

Журнал изменений проекта. Ведётся для передачи контекста между агентами (Codex, Claude Code)
и участниками команды: что уже сделано, какие интерфейсы доступны, что нельзя ломать.

**Как пользоваться, если вы агент и только подключились к проекту:**

1. Прочитайте раздел «Текущее состояние» — он описывает, что в репозитории есть прямо сейчас.
2. Найдите свою область в «Интерфейсах» — там сигнатуры и примеры, чтобы не изобретать заново.
3. Перед изменением чужого модуля посмотрите «Решения и ограничения» — там причины, по которым сделано именно так.
4. **После своих изменений добавьте запись в начало «Хронологии»** в том же формате. Коротко: что, зачем, что это меняет для других.

## Интерфейсы

### Прогнозная модель — готовый CPU-инференс

```python
import joblib
from src.weather import load_archive, select_as_of
from src.model import predict_weather

bundle = joblib.load("artifacts/ensemble/model.joblib")
archive, manifest = load_archive()
weather = select_as_of(archive, "2026-01-31T18:00:00Z", horizon_hours=48)
power = predict_weather(bundle, weather)  # вектор, те же строки, [0, 1]
```

Один вызов возвращает погоду двух турбин: 96 строк для 48 ч. Проверяется
граница доступности погоды и конец обучения относительно `as_of`.
Артефакт загружать только из доверенного источника.

**Для фронта:** готовый ансамбль на январе — MAE 0.16933, RMSE 0.25432;
1–24 ч MAE 0.15682, 25–48 ч MAE 0.18227. Это доли нормализованной мощности,
не MAPE. Факта февраля нет. Метрики `artifacts/power_curve` с фактическим
ветром не брать на график качества прогноза.

**Временные допущения:** для исследовательского обучения явно заданы UTC+5,
метка начала 10 минут, выпуск 23:00 по часам CSV. Это не ответ организаторов.
В артефакте сохранено `time_assumptions.confirmed_by_organizers=false`.

**Отличие от проекта API:** Previous Runs возвращает фиксированные заблаговременности,
а не ID одного цикла. `initialization_time` выдумывать нельзя; вместо точного
`available_at` есть `available_at_upper_bound = valid_time - offset_days*24h + 12h`.
Это политика с запасом; при отображении указывать источник оценки. Кэш содержит
реальные ответы, параметры и хэши, не моки.

### `src/storage.py` — история прогнозов

Одна DuckDB-база в файле, без сервера. Хранит **каждую** попытку спрогнозировать час, а не только последнюю:
агент возвращается к одному и тому же часу на горизонте 48 ч, потом 24 ч, потом при обновлении погоды.

```python
from datetime import datetime
from src.storage import ForecastStore, ForecastRow

with ForecastStore("data/forecasts.duckdb") as store:
    run_id = store.record_run(
        issued_at=datetime(2026, 1, 31, 12, 0),   # симулируемое «сейчас», не реальное время
        turbine_id=1,                              # только 1 или 2
        weather_source="open-meteo historical-forecast",
        weather_run="previous_day1",               # какой выпуск прогноза использован
        model_name="hist-gradient-boosting",
        model_version="v1",
        horizon_hours=48,
        trigger="scheduled",                       # scheduled | weather_update | backfill | manual
    )
    store.record_forecast(run_id, [
        ForecastRow(datetime(2026, 2, 1, 0, 0), 0.42, wind_speed=7.1, temperature=-3.0),
    ])
```

Чтение:

| Метод | Что возвращает |
|---|---|
| `store.latest(turbine_id=None)` | прогноз, который сейчас «в силе» для каждого часа (побеждает более поздний `issued_at`) |
| `store.revisions(turbine_id, target_ts)` | все прогнозы на один час по порядку, с колонкой `change` — насколько изменился |
| `store.accuracy_by_lead()` | MAE, RMSE, bias по горизонтам — только по часам, где есть факт |
| `store.summary()` | счётчики строк, для быстрой проверки |

Все возвращают `pandas.DataFrame`.

SQL-представления в базе, если удобнее запросом: `latest_forecasts`, `forecast_revisions`, `forecast_accuracy`.

CLI:

```bash
python -m src.storage init       # создать схему (единственная команда, создающая файл)
python -m src.storage summary    # счётчики строк
python -m src.storage accuracy   # ошибки по горизонтам
```

Ошибки — `StorageError` с текстом, объясняющим, что не так, вместо traceback драйвера.

## Решения и ограничения

**Почему DuckDB, а не Postgres.** Данных мало (два CSV по 6 МБ), а каждый сетевой сервис — риск, что проект
не поднимется у проверяющего. БД лежит одним файлом, поднимать нечего.

**Почему БД не в git.** `data/*.duckdb` в `.gitignore`: файл бинарный и генерируемый, восстанавливается
командой `init` плюс повторным прогоном. Итоговые прогнозы, когда появятся, нужно экспортировать
в CSV или Parquet и коммитить — именно их будет смотреть проверяющий.

**Мощность нормализована в [0, 1].** Это следует из данных: 101 различное значение, шаг 0.01.
Хранилище отвергает значения вне этого диапазона — и для прогноза, и для факта.

**`lead_hours` не передаётся, а вычисляется** из `target_ts - issued_at`. Рассогласовать горизонт и момент
выпуска невозможно. Прогноз в прошлое и выход за объявленный горизонт отклоняются.

**Февраля 2026 в исходных данных нет.** Файлы названы по 28.02.2026, но заканчиваются 2026-01-31 23:50.
Значит факта для тестового периода у нас нет, и посчитать по нему качество нельзя.
Январь 2026 полный — он и годится как отложенная выборка. В README это надо сказать прямо,
а не изображать оценку там, где измерить нечем.

**Не заполнять пропуски нулями.** У турбины 1 отсутствует 6.56% меток, крупнейший разрыв — с 18.05.2024
по 28.06.2024. Причина неизвестна: телеметрия, обслуживание или отбор записей. Нулевая мощность
в этих местах научит модель неправде.

**Турбину определяет имя файла, а не порядок в каталоге.** Исходные имена содержали
идентификаторы Google Drive, и `sorted(glob("*.csv"))` ставил турбину 2 первой: имя начиналось
с `1_`, а `_` в ASCII меньше `h` из `1hub`. Код, нумерующий файлы по порядку, связал бы координаты
турбины 1 с данными турбины 2 — площадки в 300 м друг от друга, ряды коррелируют на 0.96,
такую ошибку потом не заметить. Исправлено 13:29: файлы переименованы, `audit_data.py` читает
номер турбины из имени (`turbine_id()`), сортирует отчёт по нему и отказывается работать,
если номер не распознан или два файла заявляют одну турбину.
**Новые файлы данных именовать `turbine_<N>.csv`** — иначе аудит остановится с объяснением.

**Часовой пояс данных не определён.** В CSV меток пояса нет. До уточнения у организаторов не назначать UTC
автоматически: выбор границы часа меняет и соответствие с погодой, и доступность последнего наблюдения.

### 13:29 — План агента и контракт API (Codex)

**Добавлено:** `docs/PLAN.md`, `docs/API.md`; README дополнен текущим состоянием
и ссылками. Это проект интерфейса, маршруты ещё не реализованы.

**Разделение работ:** Codex — `src/data.py`, `src/weather.py`, `src/model.py`,
`src/agent.py`, `src/api.py`; Claude Code — существующее хранилище `src/storage.py`;
разработчики интерфейса — `frontend/`. Перед расширением чужого интерфейса
сверяться с журналом. Готовое хранилище используется через `ForecastStore`.

**Для фронта:** номера турбин — целые `1` и `2`; одно задание API может охватывать
обе турбины. Его строковый `run_id` отличается от числовых ID отдельных выпусков
в DuckDB — последние передаются как `storage_run_id` в каждой серии.

**Для интеграции:** API принимает время с зоной; адаптер нормализует его в UTC,
передаёт в текущий `TIMESTAMP` без `tzinfo` и возвращает в JSON с `Z`.
Это не назначает часовой пояс исходным CSV: его ещё нужно подтвердить.
`as_of` запроса соответствует `issued_at`, а не фактическому времени запуска.

**Замечание по метрикам:** текущий `accuracy_by_lead()` использует
`latest_forecasts` и оценивает последний выпуск на час. Для сравнения всех
ежедневных прогнозов на 24/48 часов нужен отдельный запрос по всем выпускам.

**Погода:** один запрос Open-Meteo Single Runs (`ecmwf_ifs`, цикл
`2026-01-31T12:00`) вернул 72 почасовые точки для координат ВЭС. Перед
использованием требуется проверить происхождение выпуска и время его
исторической доступности, включая задержку публикации. Примеры `previous_day1`
в интерфейсе хранилища не определяют будущий выбор погодного API.

**Зачем:** ТЗ требует цикла, в котором система пересчитывает прогноз при обновлении входных данных
и анализирует результат. Для этого нужна история: какой прогноз на какой час был выдан, когда,
на каком выпуске погоды, и как он менялся. Схема хранит каждую ревизию, а не только последнюю.

**Что это даёт другим частям проекта:**
- цикл агента пишет результат через `record_run` + `record_forecast`;
- шаг «анализ результата» читает `revisions()` — видно, куда и на сколько уехал прогноз;
- валидация на январе делается через `record_actuals` + `accuracy_by_lead()`;
- на Demo Day есть что показать SQL-запросом.

**Что нельзя ломать:** `issued_at` — это симулируемый момент принятия решения (например, 31 января 12:00),
а не время запуска скрипта. Если туда попадёт `datetime.now()`, весь бэктест потеряет смысл.

**Исправлено по ходу:** команды `summary` и `accuracy` на несуществующей базе молча создавали пустой файл
и печатали нули. Теперь они открывают базу только на чтение и сообщают, что её нет и как создать.
