## Жёсткие правила Положения, которые влияют на то, как ты работаешь с кодом

1. **Разработка только в репозитории, созданном платформой edu.astanahub.com** (п. 5.4.9, 5.4.11). Он должен быть единственным основным рабочим репозиторием с подтверждаемой историей. Сторонние закрытые репозитории = дисквалификация (п. 5.9.2). Не предлагай создавать отдельные репозитории/форки для основной разработки.
2. **Каждый час — подтверждённый промежуточный результат** (п. 5.4.8): изменения в коде/репозитории, функционал, прототип, дизайн, схема архитектуры, настроенная модель, тестирование, подготовленные данные. Делай небольшие осмысленные коммиты по мере работы; не копи всё в один финальный коммит. Если за последний час коммитов не было — напомни. Отсутствие результата за любой отчётный час — основание для дисквалификации (п. 5.9.2).
3. **Итоговая версия фиксируется на 18:00** (п. 5.4.13) — независимо от того, когда фактически заблокируется интерфейс платформы. Изменения после 18:00 не учитываются нигде, включая Demo Day (п. 5.4.14). Незакоммиченное и незапушенное не существует.
4. **Критерии оценки — в ТЗ задачи, не в Положении** (п. 5.5.1–5.5.3). Перед реализацией читать сохранённое ТЗ в `docs/hackathon/track-energy.md` вместе с критериями и обязательными требованиями. Применяются только критерии, опубликованные **до начала соревновательной части** (п. 5.5.3). Обязательные требования кейса — приоритет №1: дополнительный функционал не компенсирует невыполненное обязательное требование.
5. **Если проект не запускается по инструкциям из репозитория — команда не допускается к дальнейшему отбору, пояснения и исправления не принимаются** (п. 5.4.16, 5.6.5). Это ужесточение: в прошлой редакции эксперты могли запросить пояснения по окружению. Отсюда — запуск одной командой из чистого клона (`docker compose up` / `make run` / `./run.sh`), зафиксированные версии зависимостей, демо-данные в репо, обязательная репетиция через `scripts/check-clean-env.sh`.
6. **Ключевая функциональность должна проверяться без личных аккаунтов, подписок и закрытых учёток участников** (п. 5.6.6). Используешь внешний API — приложи демонстрационный доступ, тестовую учётную запись или сделай рабочий режим без ключа. Схема «жюри подставит свой ключ» нарушает этот пункт. В README — отдельный раздел «Проверка без собственных ключей».
7. **README обязателен и должен позволить эксперту самостоятельно развернуть решение** (п. 5.4.15, 5.6.4). Восемь обязательных блоков: описание решения и назначения · архитектура · используемые технологии · установка · запуск · зависимости · параметры окружения · порядок проверки основного сценария. Обновляй README по мере добавления фич, а не в конце.
8. **Ключевая функциональность не должна быть заменена моками.** Прямого пункта про моки в новой редакции нет, но есть запрет на выдачу чужого/готового за своё (п. 5.4.5, 5.4.6) и проверка фактической работоспособности (п. 5.6.1). Если что-то приходится замокать — явно пометь в коде (`# MOCK:`) и в README «Ограничения».
9. **Раскрывай внешние материалы** (п. 5.4.4): каждая сторонняя библиотека, открытая модель, датасет, шаблон — в раздел README «Внешние материалы» с источником и лицензией. Open-source использовать можно при соблюдении лицензий и раскрытии (п. 5.4.4.1). Участник гарантирует законность прав и отвечает за нарушение солидарно (п. 6.1.7).
10. **Заготовки разрешены с оговоркой** (п. 5.4.4.2): заранее подготовленные компоненты, собственные библиотеки, шаблоны и инфраструктура — можно, если это не готовый продукт и не основная часть решения. Основная функциональность под Задачу должна быть написана в соревновательной части 13:00–18:00. Шаблоны из `templates/` попадают сюда — раскрыть их в README отдельной таблицей. Нельзя подавать продукт, который до 13:00 уже обладал заявленной основной функциональностью (п. 5.4.5).
11. **AI-инструменты разрешены любые** (п. 5.4.12). **Codex по Положению не обязателен**, если иного не требует условие конкретной задачи, — но лендинг hackalem.ai прямо пишет «команда должна использовать Codex». Расхождение не разрешено: используем Codex и оставляем следы (упоминание в README, раздел «AI-инструменты»), а текст задачи проверяем на явное требование.
12. **Один Проект — одна Задача** (п. 5.4.1.1). Подавать одно решение по нескольким задачам нельзя.
13. **Никаких** попыток доступа к чужим системам, платформе, проектам других команд, вредоносного кода (п. 5.9.2). Не сканируй и не тестируй на проникновение ничего, кроме собственного локального стенда.
14. **Ограничение — 5 часов разработки, 13:00–18:00** (п. 3.5, 2.1). Предлагай минимальные рабочие решения, не переусложняй. Один полностью рабочий сквозной сценарий важнее трёх полурабочих.
15. **Права на результаты.** Участники предоставляют Организатору право использования Результатов безвозмездно, без ограничения по территории и сроку, включая модификацию и передачу третьим лицам (п. 6.1.2–6.1.4). В прошлой редакции права по умолчанию оставались у авторов — учитывай это, решая, что класть в репозиторий.

## Рабочее окружение и заготовки

**Рабочая машина пользователя: MacBook Air M5, macOS, Apple Silicon (`arm64`).** Оболочка — `zsh`. Порядок действий на старте — `START-HERE.md`.

- **Инструменты:** системный Python 3.9.6; для backend подготовлен Python 3.12.14 в `.tools/python`, окружение `backend/.venv`, uv 0.12.18 в `.tools/bin/uv`. `.tools/` и `.venv/` не коммитить. Зависимости — `backend/pyproject.toml` и `backend/uv.lock`.
- **Совместимость:** выбирать зависимости и контейнеры, совместимые с Apple Silicon / `arm64`.
- **Backend:** `backend/app/`, Python + FastAPI + Pydantic + DuckDB 1.5.5. Общая точка входа — `src.api:app`, запуск из корня через `make dev`. Реализованы маршруты `/api` по `docs/API.md`, очередь, события, CSV, replay и хранение состояний. Коллегин `src/storage.py` используется через `ForecastStore`; интерфейс подключения агента — `docs/backend/agent-integration.md`. Контракт v0.3 хранит `weather.sources` и `points[].weather_inputs`; для Previous Runs точные даты выпуска/публикации равны `null`, оценка проверяется по политике `previous_runs_offset_plus_12h_v1`. Допущение +12 часов не подтверждает историческую доступность. Формат и примеры — `docs/backend/weather-provenance.md`. Основная модель NOAA и policy-агент подключены; ранее проверены 29/29 выпусков через API. Frontend связан с реальным API через Next.js-прокси: запуск, статусы, журнал, результаты, CSV и история из DuckDB (GET /api/agent/runs?limit=100). Инструкции — docs/frontend-integration.md. Часовой пояс CSV и смысл временных меток требуют подтверждения. Для текущей интеграции выполнены статические проверки и экспорт OpenAPI; браузер, Docker и автотесты в этой задаче не запускались.

**Заготовки:** в репозитории есть `docs/hackathon/templates/README-template.md`. Каркас backend создаётся в этом репозитории 23.09.2026; основная модель NOAA и агент подключены к HTTP API. Если используем заранее подготовленные компоненты, раскрываем их в README по п. 5.4.4.2.

**Скрипты** (`scripts/`):
- `hourly-commit.sh "текст"` — коммит + push за отчётный час (п. 5.4.8); `--watch` напоминает каждые 50 минут
- `check-clean-env.sh` — клонирует репо в чистую папку и поднимает через Docker, то есть воспроизводит проверку экспертов (п. 5.4.16, 5.6.3)
- `test-nvidia-api.sh` — проверка ключа NVIDIA API и списка моделей

Когда предлагаешь решение — опирайся на то, что уже установлено, и не добавляй тяжёлых зависимостей без причины: каждая новая усложняет запуск в чистом окружении, а неудачный запуск снимает команду с отбора (п. 5.4.16).

## NVIDIA API и скиллы

**NVIDIA API (build.nvidia.com / NIM):** OpenAI-совместимые эндпоинты, ключ в `NVIDIA_API_KEY`. Для хакатона предпочтительнее локального GPU: эксперты запускают проект в чистом окружении, GPU у них может не быть.

⚠️ **Но помни п. 5.6.6:** проверка ключевой функциональности не должна требовать личных аккаунтов и подписок участников. Значит одного `.env.example` мало — нужен **один из**:
- демонстрационный ключ или тестовая учётная запись, приложенная к проекту допустимым образом;
- **работающий режим без ключа** (локальная детерминированная логика / записанные демо-ответы, честно помеченные), при котором основная функциональность под Задачу остаётся настоящей;
- локальная CPU-модель или алгоритм без внешних вызовов.

Ключ не коммитить. Отсутствие ключа — понятное сообщение со ссылкой на раздел README, не traceback.

**Скиллы:** доступность определять по каталогу текущей сессии. Ниже — возможные инструменты для задач проекта; наличие каждого скилла проверять перед использованием:

| Задача | Скиллы |
|---|---|
| LLM/эмбеддинги через NVIDIA API, RAG | `nemotron-*`, `nemo-retriever`, `rag-blueprint`, `rag-eval`, `dynamo-*` |
| Оптимизация: диспетчеризация, балансы мощности, маршруты бригад | `cuopt-numerical-optimization-formulation` → `cuopt-numerical-optimization-api`, `cuopt-routing-api-python` |
| Погода/прогноз для ВИЭ и нагрузки | `earth2studio-discover`, `earth2studio-data-fetch` |
| Обработка данных | `accelerated-computing-cudf`, `cupynumeric-*` |
| Осмотр ЛЭП/подстанций по фото и видео | `tao-train-visual-changenet`, `tao-train-optical-inspection`, `vss-*`, `deepstream-*` |

**Правило для конкурсной версии:** в репозиторий кладём то, что эксперт запустит в чистом окружении: NVIDIA API с fallback или CPU-реализацию (например, LP через HiGHS/OR-Tools/PuLP), с описанием ограничений в README. Локальный запуск планируем с учётом macOS / Apple Silicon; доступ к внешним вычислительным ресурсам проверяем отдельно, если они понадобятся.
